# Architecture

## System shape

StylistTG is a local-first Telegram account/profile automation platform with a React dashboard, FastAPI backend, PostgreSQL persistence, Redis/RQ execution queues, and TDLib adapters. The dashboard calls FastAPI through `/api` and polls for state.

Runtime role metadata lives in `backend/app/runtime` and documents API, scheduler, reaper, auth/profile/warmup/neuro-commenting workers, and maintenance worker boundaries without inventing queues outside `backend/app/contracts/queues.py`.

Structure audit reports are generated by `backend/scripts/structure_audit.py`; treat generated audit files as snapshots and re-run the audit before using them as current architecture input.

## Primary flows

- Dashboard requests and mutations go through `packages/api-client` or dashboard compatibility API helpers.
- FastAPI routers in `backend/app/api` validate auth/workspace context and delegate.
- Module-owned behavior should live under `backend/app/modules/`.
- `backend/app/services/` remains for shared services and compatibility wrappers.
- PostgreSQL-backed SQLAlchemy models are the source of truth for durable state.
- RQ workers execute queued auth/profile/warmup/neuro-commenting/lifecycle jobs and write final truth back to PostgreSQL.
- Account Onboarding uses `auth_jobs` for item execution and `maintenance_jobs` for private artifact expiry metadata.
- TDLib child/runtime code must not become the final database writer.

## Architecture change rule

New backend modules and architecture-affecting changes must follow `.mex/patterns/architecture-change.md` and `docs/architecture/AGENT_ARCHITECTURE_GUIDE.md` before editing.

## Source-of-truth rules

- `account_profile_state` is the source of truth for current profile state.
- `warmup_session` is the source of truth for account-preparation state.
- `account_onboarding_batch`, `account_onboarding_item`, `account_onboarding_artifact`, and `account_onboarding_event` are the source of truth for the canonical account-addition flow at `/accounts/add`.
- PostgreSQL is the dedup/persistence source of truth, not Redis.
- Redis/RQ is execution infrastructure and may be absent in tests unless explicitly required.

## Safety boundaries

- Live Telegram/TDLib behavior is disabled by default and must be explicitly approved.
- TDLib session storage is backend-only and must never be exposed to frontend diagnostics.
- Frontend risk/readiness UI is an app-known readiness score, not an anti-ban guarantee.
- Temporary safety/runtime status belongs in `.mex/status/current.md`; check it before assuming policy layers are active.
